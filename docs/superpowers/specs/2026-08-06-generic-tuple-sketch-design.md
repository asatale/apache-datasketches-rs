# Generic Tuple Sketch (Rust-defined summaries) — Design

## Purpose

Add a generic `TupleSketch<S>` to the `apache-datasketches`/`apache-datasketches-sys`
crates, where `S` is an arbitrary Rust type supplied by a downstream crate.
C++ calls back into Rust to create, combine, and clone summaries.

This is the "Future generic framework" deferred as explicitly out of scope by
[the ArrayOfDoubles design](2026-07-31-array-of-doubles-tuple-bindings-design.md).
That family has since shipped and is the immediate precedent: this design
follows its three-layer structure (C++ shim → `cxx` bridge → safe wrapper),
its `SketchError` reuse, its `Send`-not-`Sync` convention, its
`default = []` feature posture, and its 1:1-port-plus-Rust-specific testing
approach. Anything not discussed here carries over from it unchanged.

`ArrayOfDoublesSketch` is **not** modified, deprecated, or reimplemented on
top of this framework. The two coexist permanently, as its design intended:
ArrayOfDoubles remains the zero-callback fast path for the common
numeric-array case, and `TupleSketch<S>` handles arbitrary summaries at the
cost of a callback per combine.

## Scope, and the second spec

This design covers the **callback core**: building, updating, querying, and
combining generic sketches in memory, with the full operation surface
ArrayOfDoubles ships — sketch, compact snapshot, union, intersection,
a-not-b, and Jaccard similarity.

**Summary serialization is deferred to a second design.** It is the hardest
part of the feature and it is separable: the entire hazard class it
introduces — deserializing into uninitialized memory, keeping
`size_of_item` byte-exact with `serialize`, and specifying a payload
encoding — lives in the `SerDe` surface and touches nothing in the callback
core. Sequencing them means the second spec is written against a foundation
that already works, rather than landing the riskiest FFI machinery and the
riskiest memory handling in one plan. Nothing about the end state is given
up; see "Deferred to the serialization design" below for what is agreed and
waiting.

`CompactTupleSketch<S>` therefore exists in this design as the result of
`compact()` and of every set operation, but has no `serialize()` yet.

## What upstream actually demands of a `Summary`

The following was verified against the vendored headers rather than assumed,
because the whole design depends on it.

The entry table allocates **raw memory** and placement-news every entry
(`theta/include/theta_update_sketch_base_impl.hpp:47,67,211,241,273`). It
therefore never default-constructs a `Summary`, which matters because
`rust::Box` is not default-constructible (`Box() = delete`, `rust/cxx.h:298`).
The operations it does require split cleanly by cost:

| Operation | Where | Cost |
|---|---|---|
| **move**-construct | rehash, resize, compaction (`..._impl.hpp:217,246,292`) | native to `rust::Box`; **no trampoline** |
| **destroy** | table teardown, entry eviction | generated by cxx; **no trampoline** |
| **copy**-construct | whole-sketch copy (`..._impl.hpp:70`), update→compact conversion | **clone trampoline**, off the update path |

`rust::Box`'s move constructor nulls the source (`rust/cxx.h:775-777`) and its
destructor null-checks before dropping (`rust/cxx.h:796-800`), so moved-from
entries are safe to destroy — which is what makes the mass-move rehash path
sound.

The net callback surface is **three C++→Rust trampolines**: `clone`,
`union_combine`, and `intersection_combine`. This is substantially smaller
than the nine the ArrayOfDoubles design sketched, and none of them fires on
a plain `update()` to an existing key except the combine itself.

## Why type erasure, and why not the alternatives

**Chosen: a type-erased `DynSummary` holding a `rust::Box`.** The C++ side
gets exactly one instantiation, `tuple_sketch<DynSummary>`, regardless of how
many summary types exist anywhere in the dependency graph. `DynSummary` is a
small C++ class wrapping an opaque `extern "Rust"` object; its move
constructor and destructor are `rust::Box`'s own, and only its copy
constructor is hand-written, calling the clone trampoline. Cost is one
pointer indirection and one dynamic dispatch per callback — on operations
that already cross FFI.

**Rejected: a fixed-size inline buffer.** `DynSummary` as an `N`-byte array
plus a function-table pointer would make moves and copies `memcpy`,
eliminating the clone trampoline and the per-entry allocation entirely. It is
materially faster, but it restricts summaries to `Copy` types that fit in `N`,
excluding anything owning heap memory. It remains available later as an
opt-in specialization for `Copy` summaries without changing the public trait;
building two tiers now would be premature.

**Rejected as infeasible: monomorphizing per summary type.** Generating a real
C++ instantiation per concrete `S` would be fastest and needs no dynamic
dispatch, but a downstream crate cannot inject `cxx-build` codegen into this
crate's `build.rs`. It could only ever serve summaries defined inside this
crate, which defeats the purpose.

## Where the trait lives

`cxx` requires an `extern "Rust"` opaque type to be defined in the same crate
as the bridge declaring it. That constraint — flagged as an open question by
the ArrayOfDoubles design — resolves as a two-trait split:

- **`apache-datasketches-sys`** owns a concrete `RustSummary` (the
  `extern "Rust"` opaque type, holding a `Box<dyn RawSummaryOps>`) and the
  minimal `RawSummaryOps` trait the trampolines call. This satisfies cxx's
  same-crate rule and keeps the sys crate's public surface as
  minimal-and-unstable as established convention.
- **`apache-datasketches`** owns the ergonomic `TupleSummary` that users
  implement, plus a private adapter type carrying the blanket
  `impl<S: TupleSummary> RawSummaryOps for Adapter<S>`.

Users never name anything from the sys crate.

Because `RawSummaryOps` receives `&dyn` for the other operand, the adapter
downcasts via `Any` to recover `S`. The typed façade makes a mismatch
unreachable through the public API — `TupleUnion<S>` accepts only
`TupleSketch<S>` — so this is a defensive check, never an unchecked cast.
A failed downcast aborts with an internal-invariant message.

## The update path: the `Update` type never crosses FFI

Upstream's update policy is `create()` followed by
`update(Summary&, const Update&)`, which would force the user's update value
across the boundary as a second erased type. This design avoids that.

`sketch.update_u64(key, &value)` proceeds as:

1. Rust computes `S::create(&value)` — an owned `S`, on the stack
2. Rust wraps it and passes a **borrowed** reference to C++
3. C++ hashes, finds the slot, and either clones the borrowed summary into a
   new entry (new key) or calls the combine trampoline against the existing
   entry

`Self::Update` therefore stays purely Rust-side, and an allocation occurs only
on a genuine insert rather than on every update. The C++ instantiation is
`update_tuple_sketch<DynSummary, DynSummary, DynUpdatePolicy>` — the sketch's
`Update` type is `DynSummary` itself, which is what removes the need for a
second erased type.

### `DynSummary` needs an empty state, and why

Upstream's update path is fixed (`tuple/include/tuple_sketch_impl.hpp:213-224`):

```cpp
auto result = map_.find(hash);
if (!result.second) {
  S summary = policy_.create();                 // no arguments
  policy_.update(summary, std::forward<UU>(value));
  map_.insert(result.first, Entry(hash, std::move(summary)));
} else {
  policy_.update((*result.first).second, std::forward<UU>(value));
}
```

`create()` takes **no arguments** and must return an `S`. There is no
universal identity element for an arbitrary user-defined summary — `min` has
no finite one, "first wins" has none at all — so `create()` cannot construct
a meaningful summary and the trait must not be made to supply one.

`DynSummary` therefore holds `std::optional<rust::Box<RustSummary>>` and is
default-constructible to a disengaged state. `DynUpdatePolicy::update` reads:

- target disengaged → clone the incoming summary into it (the insert path)
- target engaged → call the `union_combine` trampoline

The disengaged state is **transient and never stored**: it exists only
between the `create()` and `update()` calls on consecutive lines above, and
the result is immediately moved into the table. Every entry the table holds
is engaged. `DynSummary`'s copy constructor propagates disengagement rather
than asserting, so a copy is always well-defined.

Allocation behaviour is unchanged by this: `create()` allocates nothing, the
clone on insert allocates once, and the move into the table allocates
nothing. Updating an existing key still allocates zero.

**Union and intersection need no `create()` at all**, which is worth noting
because it constrains their policies less. Union inserts the incoming entry
directly on a new key and invokes `policy_(Summary&, const Summary&)` only on
collision (`theta/include/theta_union_base_impl.hpp:50-52`); intersection
invokes it only on a match (`theta_intersection_base_impl.hpp:70-72`). Both
policies are plain two-summary combines against always-engaged operands.

A consequence worth stating plainly: a panic in `create` is an **ordinary
Rust panic**, because it runs entirely Rust-side before any C++ call. It
propagates to the caller and is catchable. Only the three trampolined methods
abort. `create` is where most user logic lives.

## Public Rust API

Generic types live at `apache_datasketches::tuple::generic`, leaving
`tuple::ArrayOfDoublesSketch` and its siblings exactly where they are. This
is non-breaking, and it keeps both under the existing `tuple` feature — which
the ArrayOfDoubles design chose that feature name specifically to allow.

### The trait users implement

```rust
pub trait TupleSummary: Clone + Send + 'static {
    /// The value passed to the sketch's `update_*` methods.
    type Update: ?Sized;

    /// Build a summary from one update value.
    fn create(update: &Self::Update) -> Self;

    /// Merge `other` into `self`: repeated updates to a key, and union.
    fn union_combine(&mut self, other: &Self);

    /// Merge `other` into `self` for intersection.
    fn intersection_combine(&mut self, other: &Self);
}
```

`Clone` is a supertrait rather than a `clone_summary` method: it is exactly
what the copy trampoline needs, and it is what a Rust user expects. `Send`
matches the crate-wide convention. `'static` is required for the `Any`
downcast. `Update: ?Sized` allows `Update = str` or `Update = [f64]` without
forcing an owned type on the caller.

**`intersection_combine` is required, not defaulted.** Defaulting it to
`union_combine` would be friendlier and would match what ArrayOfDoubles does,
but upstream's own header states there is no sensible default intersection
policy "since it is not clear in general", and a silently-wrong intersection
semantic surfaces late and is hard to attribute. The cost is one method for
users who never intersect.

### Types

Each mirrors its ArrayOfDoubles counterpart:

- **`TupleSketchBuilder<S>`** — `lg_k`, `resize_factor`, `p`, `build()`.
- **`TupleSketch<S>`** — the same eleven `update_*` key overloads
  (`u64`/`i64`/`u32`/`i32`/`u16`/`i16`/`u8`/`i8`/`f64`/`str`/`bytes`), each
  taking a key plus `&S::Update`; `trim`, `reset`, the eight shared queries,
  `entries()`, `compact(ordered)`.
- **`CompactTupleSketch<S>`** — the eight shared queries plus `entries()`.
  No `serialize()` in this design.

"The eight shared queries" throughout means the surface every family in this
crate exposes: `get_estimate`, `get_lower_bound(num_std_dev)`,
`get_upper_bound(num_std_dev)`, `is_empty`, `is_estimation_mode`,
`is_ordered`, `get_theta`, and `get_num_retained`. The two bound methods
return `Result` for out-of-range `num_std_dev`, as elsewhere.
- **`TupleUnionBuilder<S>` / `TupleUnion<S>`** — `update`,
  `get_result(ordered)`, `reset`.
- **`TupleIntersection<S>`** — `new()`, `update`, `get_result(ordered)`,
  `has_result()`.
- **`TupleAnotB<S>`** — `new()`, `compute(a, b, ordered)`.
- **`tuple_jaccard_similarity<S>(a, b)`** — returning the existing
  `tuple::JaccardBounds` rather than a third identical struct.
- **`TupleInput<S>`** — sealed, over `TupleSketch<S>` and
  `CompactTupleSketch<S>`, mirroring `ArrayOfDoublesInput`.

### Two deliberate differences from ArrayOfDoubles

**`update_*` is infallible**, returning `()` rather than `Result`. The
slice-length validation that forced `Result` on ArrayOfDoubles — upstream
indexing a caller-supplied array without a bounds check — has no analogue
when the summary is a typed Rust value constructed by the user's own
`create`.

**Set operations take no operand-mismatch `Result` either.** The
`num_values` agreement ArrayOfDoubles validates at runtime is enforced here
by the type system: `TupleUnion<S>` accepts only `TupleSketch<S>` or
`CompactTupleSketch<S>`. The generic API is genuinely the simpler surface.

`TupleIntersection::get_result` still returns `Result`, for the existing
`EmptyIntersection` case.

### `entries()`

Returns `impl Iterator<Item = (u64, S)>` — owned summaries, for the same
reason ArrayOfDoubles returns owned `Vec<f64>`: cxx cannot hand back a live
C++ iterator, and borrowing from a collection built inside the method is a
self-referential borrow. `S: Clone` is already required, so this adds nothing
to the trait. A borrowing `for_each_entry` is a natural later addition if
cloning large summaries proves costly; it is deliberately not in v1.

## Safety

**Panics in trampolined methods are safe but fatal.** cxx wraps every
`extern "Rust"` function in `prevent_unwind`
(`cxx-1.0.198/src/unwind.rs`), converting a panic into a deterministic abort
through a double-panic guard — explicitly not undefined behaviour, but the
process does terminate.

Doing better was considered and rejected. Upstream's combine policy returns
`void`, so there is no way to signal C++ that an entry failed and have it
unwind the insert. Catching the panic and continuing would leave the sketch
memory-safe but logically undefined, which is worse than stopping. The design
therefore accepts abort, with one improvement: the adapter catches the panic
first and emits a message naming the trait method and summary type before
aborting, turning an unexplained fatal signal into something actionable.

The trait documentation must state which three methods are abort-on-panic
(`union_combine`, `intersection_combine`, `Clone::clone`) and that `create`
is not.

**No uninitialized memory.** That hazard class belongs entirely to
`SerDe::deserialize` and therefore to the serialization design. Every
`DynSummary` constructed here is placement-newed from a fully-constructed
value — a clone or a move — never from raw bytes.

**No reentrancy hazard.** User code inside a combine holds `&mut self` and
`&other` and has no handle to the sketch, so it cannot re-enter a sketch that
is mid-mutation.

**The policy structs must be stateless and default-constructible.** This is
not incidental: upstream's `jaccard_similarity_base::jaccard()` internally
builds a scratch union via `typename Union::builder()` and a scratch
intersection via `Intersection(seed)`, both with default-constructed
policies. ArrayOfDoubles had to reason carefully about this because its
policy carries `num_values`; here the policies carry nothing at all —
they dispatch through the summary object itself — so default construction is
trivially correct and the subtlety disappears. Keeping the policies stateless
is therefore a design constraint, not just a simplification.

## Error handling

Reuses the existing `SketchError` with **no new variant**, consistent with
every prior family. Builder validation (`lg_k`, `p`) maps to `InvalidConfig`
via the established C++-exception-to-`Result` path; an intersection with no
result maps to `EmptyIntersection`.

## Concurrency

`TupleSketch<S>`, `CompactTupleSketch<S>`, `TupleUnion<S>`,
`TupleIntersection<S>`, and `TupleAnotB<S>` are all `Send` and not `Sync`,
unchanged from every prior family.

For that to be sound rather than asserted, the bound has to hold all the way
down: `TupleSummary` requires `S: Send`, the sys-crate `RustSummary` holds a
`Box<dyn RawSummaryOps + Send>` (the `+ Send` is load-bearing and must not be
dropped), and the safe wrappers carry `unsafe impl<S: TupleSummary> Send`
with no `Sync` counterpart. Without `+ Send` on the boxed trait object, a
sketch could carry a non-`Send` summary across threads while the wrapper
still claimed `Send`.

check enforces it at build time.

## Testing

**Behavioural conformance against ArrayOfDoubles.** Implement an
ArrayOfDoubles-equivalent summary on the generic framework — `Doubles(Vec<f64>)`
with summing combines — and assert it produces identical estimates, retained
counts, theta, and entries to the shipped `ArrayOfDoublesSketch` over the same
inputs. The reference implementation is already in-tree and tested, so the
fixture costs nothing, and it validates the whole callback core against
known-good behaviour. Byte-level parity is the serialization design's
conformance test; this one is behavioural.

**Clone/drop accounting is the highest-value test here**, because the failure
mode is silent. A summary type with static clone and drop counters, asserted
to balance after the sketch is dropped, exercised through table resize past
`k` (the mass-move rehash path), `compact()`, and every set operation. A leak
or double-free in the `rust::Box` ownership dance appears here and
essentially nowhere else. Miri cannot substitute — it does not execute C++
FFI. ASan is a useful optional extra, not a replacement.

**Four summary types, each stressing something different:**

- `Count(u64)` — trivial `Copy` summary, the cheapest path.
- A heap-owning summary (`Vec<f64>` or `String`) — clone and drop correctness.
- One with a distinct, unsized `Update` (`Update = str` feeding a length
  histogram) — proves the associated type works and never crosses FFI.
- One where **union and intersection semantics genuinely differ** — union
  sums, intersection takes the minimum. Two identically-shaped callbacks are
  easy to cross-wire, and if both do the same thing no test can detect a
  swap. This is the direct lesson from the a-not-b operand-transposition
  finding on the ArrayOfDoubles branch.

**Estimation mode from the start.** Every set operation gets coverage above
`k = 4096`, not only below it. The ArrayOfDoubles family shipped with every
set-op test in exact mode and needed a retrofit round to fix; that is not
repeated here.

**Panic containment gets a real test.** The claim is a clean abort with a
diagnostic message, so one test re-invokes the test binary as a subprocess
with an environment variable that triggers a panicking `union_combine`, and
asserts the process aborts with the expected message on stderr. Otherwise
that guarantee is untested prose.

**Standard per-family coverage** carries over unchanged: sys-crate link tests
per bridge, safe-crate smoke tests per type, `Send` verification, and
feature-combination builds.

## Deferred to the serialization design

Agreed in principle, specified separately once this core is proven:

- **Envelope compatibility.** The serialized sketch envelope — preamble,
  flags, seed hash, theta, entry count, hash array — will be byte-identical
  to upstream's, so any C++ or Java Tuple reader can parse the structure and
  recover the keys.
- **A compositional codec** rather than a menu of blessed encodings:
  fixed-width primitives little-endian, `Vec`/`String` length-prefixed,
  structs composing field-wise via a derive macro.
- **A shipped C++ `SerDe` header** in the sys crate implementing the matching
  format, so a C++ consumer includes our header rather than reimplementing a
  format from prose. This is what makes cross-language interop real rather
  than aspirational.
- **Byte-parity conformance**: the generic framework configured as
  ArrayOfDoubles must reproduce its exact serialized bytes.
- The three hazards that come with it — deserializing into uninitialized
  memory, `size_of_item` agreeing byte-exactly with `serialize`, and
  self-describing encodings for variable-length summaries.

## Out of scope

- Summary serialization and cross-language interop — the separate design
  above.
- The fixed-size-inline-buffer specialization for `Copy` summaries — a
  possible later optimization that does not change the public trait.
- Reimplementing `ArrayOfDoublesSketch` on this framework. The two coexist
  permanently by design.
- A borrowing `for_each_entry` iteration API.
- Exposing a custom seed — default-seed-only, as in every prior family.
- Sketch families other than HLL, Theta, CPC, and Tuple.
- CI/CD and prebuilt binaries — unchanged from prior designs.
